## Ловушки

### Ловушка 1: `payment` — неполная сущность

**Какие атрибуты добавил в `payment` и почему** (BR-8.2):

```
pay_type              payment_type   тип оплаты, BR-8.2 и BR-8.6
amount                numeric(8,2)   сумма попытки, BR-8.2 и BR-8.4
transaction_id        text           номер транзакции у провайдера, BR-8.3
transaction_timestamp timestamp      дата и время транзакции, BR-8.2
status                payment_status успех / ошибка / в_обработке, BR-8.2

Все поля NOT NULL. Данных карты нет, только номер транзакции (BR-8.5).
transaction_id это номер, который выдаёт платёжная система, а не ключ нашей
таблицы, поэтому требование B.4 "все PK uuid" к нему не относится. Его формат
выбираем не мы: в номере бывают буквы и дефисы, длина у разных систем разная.
Поэтому text без ограничения длины, проверка только "не пусто" и UNIQUE.

Сумму попытки (BR-8.4) проверяет составной FK:
    FOREIGN KEY (order_id, amount) REFERENCES "order" (order_id, total_amount)
Платёж на другую сумму база не примет. Для этого FK на "order" есть
UNIQUE (order_id, total_amount).

Две успешные попытки у одного заказа не даёт сделать частичный индекс:
    CREATE UNIQUE INDEX payment_one_success_uq ON payment (order_id) WHERE status = 'успех';
Заказ совсем без успешной попытки допустим, иначе не было бы статусов
'ожидает' и 'ошибка' из BR-8.7.
```

**Где хранится тип оплаты — `payment` или `order`** (BR-8.6):

```
В payment. Клиент может начать платить картой, получить ошибку и заплатить
наличными, то есть у одного заказа бывают попытки разных типов.
```

### Ловушка 2: `order.address_id` — принадлежность клиенту (BR-7.4)

**Как обеспечено, что адрес доставки принадлежит клиенту:**

```
Составным FK на таблицу связей:
    CONSTRAINT order_client_address_fk FOREIGN KEY (client_id, address_id)
        REFERENCES client_address (client_id, address_id) ON DELETE RESTRICT

Пара (client_id, address_id) из заказа должна быть в client_address, поэтому
на чужой адрес заказ не оформить, т.к. и адрес, и айди клиента должны совпасть одновременно. Ссылаемся на первичный ключ client_address.
Обычные FK на client и address тоже есть, они из ERD.
```

### Ловушка 3: `order_structure` — один ресторан в заказе (BR-7.3)

**Как обеспечено, что все блюда из `order.restaurant_id`:**

```
Триггер order_structure_same_restaurant (файл 02_rules.sql), AFTER INSERT OR UPDATE
на order_structure. Сравнивает ресторан блюда с рестораном заказа, если они
разные, выдаёт ошибку "блюдо ... не из ресторана заказа ...".

Ключ тут не подходит: для него в order_structure нужен restaurant_id, а он
зависит только от order_id, то есть от части ключа. Это нарушение 2НФ

Еще два триггера (в файле 05_restaurant_locks.sql) закрывают другой потенциальный баг:
нельзя сменить ресторан у заказа, в котором уже есть блюда, и нельзя перенести
в другой ресторан блюдо, которое уже заказывали.
```

### Ловушка 4: `review` — полиморфизм (BR-9.1)

**Как реализована валидность `review.entity_id`:**

```
Оставил полиморфизм как в ERD: entity_type говорит, на что отзыв, entity_id
хранит id блюда, ресторана или заказа. Ключ на entity_id сделать нельзя т.к. он
ссылается на разные таблицы. 

Ключ при создании привязывается к одной таблице и проверяет каждое значение только в ней. 

Например, если сделать FK на product, то отзыв на ресторан не вставится: id ресторана в product нет. 

А сказать ключу "если entity_type = блюдо, ищи в product, если ресторан, то в restaurant"
нельзя, FK не смотрит на другие столбцы строки

Вместо него:
1. FK (order_id, client_id) на "order" (order_id, client_id): отзыв пишет
   клиент этого заказа (BR-9.2). Для него на "order" есть UNIQUE (order_id, client_id).
2. CHECK (entity_type != 'заказ' OR entity_id = order_id): отзыв на заказ
   относится к своему заказу (BR-9.2)
3. Триггер review_matches_order: отзыв на блюдо только если блюдо есть в заказе,
   отзыв на ресторан только на ресторан заказа (BR-9.2)
4. UNIQUE (entity_type, entity_id, order_id): один отзыв на объект в заказе (BR-9.5)
```

## FK-ограничения

```
По умолчанию ON DELETE RESTRICT. Он не даёт удалить строку, пока на неё
ссылается хотя бы одна строка другой таблицы. Ошибка выдаётся сразу,
на этом же DELETE.

Почему не CASCADE. По BR-3.5 история заказов должна сохраняться. С CASCADE
удаление клиента, ресторана, курьера или блюда молча удалило бы его заказы,
а вместе с ними позиции, платежи и отзывы. Пропали бы финансовые данные,
и пересчитались бы рейтинги. Вместо удаления в BR есть статусы: ресторан
'неактивен' (BR-4.3), блюдо 'архив' (BR-5.5), курьер 'уволен' (BR-6.3).
Строка остаётся, и старые заказы продолжают на неё ссылаться.

Почему не SET NULL. Все эти столбцы NOT NULL (BR-11.3): заказ без клиента,
ресторана или курьера, позиция без блюда и платёж без заказа не имеют смысла.
SET NULL упёрся бы в NOT NULL и тоже не дал бы удалить, только с менее
понятной ошибкой.

Почему RESTRICT, а не NO ACTION по умолчанию. Результат одинаковый, удаление
не пройдёт. Разница в моменте проверки: NO ACTION проверяется в конце команды
и может быть отложен до COMMIT, RESTRICT проверяется сразу. Откладывать здесь
нечего, поэтому я написал RESTRICT явно у всех FK, кроме двух CASCADE ниже,
чтобы решение было видно в схеме.

CASCADE стоит только там, где дочерняя строка без родителя ничего не значит:
- client_address.client_id: привязка адреса к клиенту. Сам адрес остаётся,
  на address стоит RESTRICT (BR-3.5). Клиента с заказами всё равно не удалить,
  его держит RESTRICT из "order".
- order_structure.order_id: позиции заказа. Заказ с платежами или отзывами
  всё равно не удалить, его держит RESTRICT из payment и review.
```

## Нормализация (3НФ)

```
1НФ: в каждом поле одно значение. В ERD у курьера одно поле FIO, у ресторана
одно поле company_details, и BR-4.5 тоже называет реквизиты "полем". Но ФИО
это фамилия, имя и отчество, а реквизиты это ИНН, ОГРН и расчётный счёт
(BR-4.5). В одном поле их не найти и не проверить по отдельности, поэтому
я разбил их на столбцы: у курьера last_name, first_name, middle_name,
у ресторана inn, ogrn, bank_account. Отчества может не быть, поэтому
middle_name необязательное.

2НФ: в таблицах с составным ключом (client_address, order_structure, courier_pay)
неключевые поля зависят от всего ключа: quantity от пары "заказ, блюдо",
amount от тройки "курьер, год, месяц".

3НФ: данные ресторана, клиента, курьера и адреса лежат в своих таблицах,
в "order" только их id

Особые случаи:
- commission и total_amount зависят от order_amount. Хранятся, потому что они
  есть в ERD, а записать неверное значение не дают два CHECK (см. DEFAULT и GENERATED).
- product.rating и restaurant.rating хранятся готовыми, чтобы не считать среднее
  при каждом показе меню. Обновляет их триггер review_rating_change.
- review.entity_id + entity_type: полиморфная ссылка, см. ловушку 4.
```

## Триггерные функции

Кроме `rating_change` из ТЗ, в схеме есть ещё шесть триггерных функций. Вручную их не вызывают. Пять из них проверяют правила из BR, которые нельзя записать через FK, CHECK или UNIQUE без нарушения 2НФ или изменения схемы из ERD (см. «Рассмотрел и отклонил» ниже): CHECK видит только свою строку, а FK проверяет только, что значение есть в другой таблице. По BR-11.4 такие правила должна проверять база, а не приложение. Шестая пересчитывает статус оплаты заказа.

| # | Функция | Файл | Триггер и когда срабатывает | BR | Что делает |
|---|---|---|---|---|---|
| 1 | `check_same_restaurant` | `02_rules.sql` | `order_structure_same_restaurant`, после вставки и изменения позиции заказа | BR-7.3 | проверяет, что блюдо из того же ресторана, что и заказ (ловушка 3) |
| 2 | `forbid_order_restaurant_change` | `05_restaurant_locks.sql` | `order_restaurant_locked`, до изменения `restaurant_id` заказа | BR-7.3 | запрещает сменить ресторан у заказа, в котором уже есть блюда |
| 3 | `forbid_product_restaurant_change` | `05_restaurant_locks.sql` | `product_restaurant_locked`, до изменения `restaurant_id` блюда | BR-7.3 | запрещает перенести в другой ресторан блюдо, которое уже есть в заказах |
| 4 | `check_order_has_items` | `02_rules.sql` | `order_has_items` (вставка заказа) и `order_structure_keeps_items` (удаление и перенос позиции), оба при `COMMIT` | BR-7.14 | проверяет, что в заказе есть хотя бы одно блюдо |
| 5 | `check_review_matches_order` | `02_rules.sql` | `review_matches_order`, после вставки и изменения отзыва | BR-9.2 | проверяет, что отзыв оставлен на блюдо из этого заказа или на ресторан этого заказа (ловушка 4) |
| 6 | `recalc_pay_status` | `03_recalc.sql` | `payment_pay_status`, после вставки, изменения и удаления попытки оплаты | BR-8.7 | пересчитывает `pay_status` заказа |

Функции 2 и 3 (запреты смены ресторана) нужны, чтобы нельзя было обойти функцию 1, `check_same_restaurant`. Она срабатывает только на `order_structure`. Если поменять ресторан у заказа или у блюда, в заказе окажутся блюда чужого ресторана.

Функция 4, `check_order_has_items`, проверяет в момент `COMMIT`, а не сразу, потому что заказ вставляется раньше своих позиций. Если заказ удаляют целиком, его позиции удаляются через `CASCADE`. Это не ошибка, поэтому функция сначала проверяет, что заказ ещё есть.

Функция 6, `recalc_pay_status`, работает как `rating_change`: итог хранится в таблице, триггер его пересчитывает. Если есть успешная попытка, статус `'оплачен'`. Если все попытки с ошибкой, `'ошибка'`. Иначе `'ожидает'`. Столбец `GENERATED` тут не подходит, он не может читать другую таблицу.

Рассмотрел и отклонил:
- Вместо функций 1-3 для BR-7.3 можно добавить `restaurant_id` в `order_structure` и сделать составные FK на `"order" (order_id, restaurant_id)` и `product (product_id, restaurant_id)`. Не стал: `restaurant_id` в `order_structure` зависит только от `order_id`, то есть от части ключа, это нарушает 2НФ.
- Вместо функции 5 для BR-9.2 можно сделать отдельные столбцы `product_id` и `restaurant_id` с составными FK на `order_structure` и `"order"`. Не стал: это меняет схему из ERD и `rating_change` из ТЗ. Оставил полиморфную ссылку, как в ERD.

## Отличия типов от ERD

По BR-11.6 длины и точность выбираю сам. Отличия:

- `client.password` `char(32)`: MD5 всегда 32 символа.
- `phone_number` `char(12)`: `+7` и 10 цифр, в `char(11)` не помещается.
- `review.rating` `smallint`: оценка целая от 1 до 5. Средний рейтинг блюда и ресторана `numeric(3,2)`.
- Коэффициенты `numeric(2,1)`, количество `numeric(8,3)` (бывает 0.5 кг).
- Цена блюда `numeric(6,2)`, до 9 999,99 ₽: блюдо дороже 10 000 ₽ в доставке не встречается.
- Суммы заказа, платежа и выплаты курьеру `numeric(8,2)`, до 999 999,99 ₽: с запасом на большой заказ и на месячную выплату. У всех сумм один тип, потому что `total_amount` складывается из двух других, а сумма платежа сверяется с ней через составной FK.
- `payment.transaction_id` `text`, см. ловушку 1.

## Прочие решения

1. BR-8.1 говорит "ровно одна успешная попытка", а BR-8.7 описывает заказы без неё. Схема запрещает вторую успешную попытку, а заказ без успешной разрешает.
2. **Повторный вызов `insert_test_data` добавляет данные** (C.9). Каждый вызов создаёт свои строки, уникальные поля (логин, улица, телефон) не пересекаются с прошлыми вызовами. Начать с нуля можно через `erase_test_data()`.
3. Генератор не вызывает функции схемы (`samples/all_examples.sql`, раздел 10): рейтинги, статус оплаты и выплаты считает сам. Иначе на каждый отзыв и платёж срабатывали бы триггеры `rating_change` и `recalc_pay_status`. Поэтому на время работы процедуры триггеры выключены на уровне сессии: `SET session_replication_role = replica`. Вместе с ними на это время выключаются и проверки FK и триггеры BR-7.3, BR-7.14, BR-9.2, поэтому генератор сам берёт только существующие id и блюда ресторана заказа. Под `inspector` генератор тоже должен запускаться, поэтому в `grants.sql` ему выдано право менять этот параметр. Это право в бэкап не попадает, поэтому после восстановления нужно выполнить `grants.sql`. Выключать триггеры на уровне таблиц (`ALTER TABLE ... DISABLE TRIGGER`) не стал: так может только владелец таблицы, а `inspector` им не является, и такая команда действует на все сессии, а не только на генератор.
4. По паттернам сделано не всё, где этого не дают тесты и BR: у клиента ровно 4 адреса (BR-11.7, все `value * 4` клиентских адреса должны использоваться), у заказа одна попытка оплаты (C.3 ждёт `value * 5` платежей). Выплаты генерируются за последние 6 месяцев, включая текущий, как в паттерне. Курьеры нанимаются в первом из этих месяцев, а увольняются только в текущем, поэтому запись есть у каждого курьера за каждый месяц, а коэффициент на следующий месяц уволенным не назначается (BR-10.6).
5. Месяц заказа для зарплаты считается по `order_timestamp`, как в C.8.
6. `add_product` сохраняет переданный `p_rating`: FOOD-104 требует принимать все атрибуты `product`, кроме id. После первого отзыва `rating_change` ставит среднее.
7. BR-6.6 схемой не гарантируется, как и сказано в правиле. В генераторе первый курьер всегда `'свободен'`.
8. E.3 в исходном виде падает: отзыв идёт от случайного клиента на чужой заказ, а BR-9.2 это запрещает. Я сделал по BR, пример на правильных данных есть в `tests.md`.
9. **`erase_test_data` без `SET CONSTRAINTS`.** В первой версии процедура начиналась с `SET CONSTRAINTS ... IMMEDIATE`. Эти строки появились после код-ревью, которое по моей просьбе делал ИИ-ассистент. Он нашёл случай: если вызвать `insert_test_data` и `erase_test_data` в одной транзакции (например, в DBeaver без автокоммита), очистка падала с ошибкой `cannot TRUNCATE "order" because it has pending trigger events`. Причина в отложенной проверке BR-7.14: она выполняется только при `COMMIT`, а `TRUNCATE` не работает, пока в транзакции есть невыполненные отложенные проверки. `SET CONSTRAINTS ... IMMEDIATE` запускает их сразу, и после этого `TRUNCATE` проходит. Я с ним согласился и добавил эти строки. Потом я их убрал: это страховка от случая, которого нет ни в BR, ни в тестах. При автокоммите обычный `CALL erase_test_data()` идёт в своей транзакции и работает без них. Сейчас `insert_test_data` выключает триггеры через `session_replication_role = replica`, поэтому после неё отложенных проверок нет, и вызов в одной транзакции тоже проходит. Ошибка остаётся, только если в той же транзакции перед очисткой вставить заказ вручную.
10. **Статус оплаты в тестовых данных.** На заказ одна попытка оплаты (C.3), поэтому статус заказа выбирается случайно, а статус попытки следует из него по BR-8.7: `'оплачен'` и `'успех'`, `'ошибка'` и `'ошибка'`, `'ожидает'` и `'в_обработке'`. Статус оплаты не связан со статусом заказа: BR не запрещает, например, доставленный заказ с ошибкой оплаты.
11. **`rating_change` пересчитывает один объект отзыва:** `coalesce(NEW.entity_id, OLD.entity_id)`. При вставке и изменении это новый объект, при удалении старый. Если у отзыва поменять сам объект (`entity_id`), рейтинг пересчитается только у нового, у старого останется прежним до следующего изменения его отзывов. Отзыв пишут на конкретное блюдо, ресторан или заказ (BR-9.2), переносить его на другой объект не штатная операция. Это расходится с критерием FOOD-105 «рейтинги пересчитываются для затронутых сущностей», но так изменение отзыва об одном объекте никогда не меняет рейтинг другого.
12. **`get_statistic`: лучшее блюдо и лучший клиент через `max()` и `JOIN`.** Из каждого ресторана нужно взять одну строку: блюдо с наибольшим количеством продаж и клиента с наибольшим числом заказов. Подзапрос с `max()` и `GROUP BY restaurant_id` находит максимум по ресторану, `JOIN` с ним оставляет только строки с этим максимумом. Если таких строк несколько, FOOD-106 требует вернуть случайное блюдо и случайного клиента, поэтому из оставшихся `DISTINCT ON (restaurant_id) ... ORDER BY restaurant_id, random()` берёт одну случайную. Подзапрос стоит в `JOIN`, а не в `IN`, по BR-11.8. Таблица `"order"` читается один раз (CTE `delivered`), подзапрос читает уже посчитанный CTE.

    Выбрал по нагрузочному тесту четырёх вариантов: `DISTINCT ON` по всем строкам, ранжирование `row_number()`, агрегация с подзапросом (`max()` и `JOIN`), массив `(array_agg(... ORDER BY ...))[1]`. Медиана 7-9 запусков, мс, PostgreSQL 18:

    | Данные | `DISTINCT ON` | `row_number()` | `max()` и `JOIN` | массив |
    |---|---|---|---|---|
    | вся функция на `insert_test_data(1000)` | 27,5 | 28,4 | 31,8 | 32,0 |
    | только выбор клиента, 1000 ресторанов по 50 клиентов | 45 | 33 | 21 | 33 |
    | то же, по 500 клиентов (500 тыс. строк) | 799 | 551 | 253 | 516 |
    | то же, по 2000 клиентов (2 млн строк) | 3434 | 2369 | 914 | 2073 |

    На тестовом объёме разница меньше 5 мс. На больших данных `max()` и `JOIN` быстрее остальных в 2-4 раза: сортируются только строки с максимумом, а остальные три варианта сортируют все строки. `row_number()` к тому же оконная функция, а BR-11.8 просит не использовать окна там, где хватает агрегации.
